## Scenario record boundary

A numeric scenario record requires `review_status="accepted"`, `disposition="rated"`, the current resolver `version`, a nonempty `review_reference`, a SHA-256 `provenance_digest`, a known non-empirical `basis_category`, and a nonempty conditional-event rationale.
Allowing the scenario basis type does not accept an individual record.
Missing, pending, rejected, malformed, or contradictory governance remains nonnumeric.
Optional `applicable_queries` must contain exact query identities, never a substring expression.

Every field of `LikelihoodLookupKey.to_dict()` except the dimension label is explicitly bound.
This includes scenario ID/version, snapshot, foothold, ordered full canonical history, outcome work unit/technique, actor/source/target, method, budget, horizon, boundary/scope, authentication/resource context, and policy.
An explicit null optional context binds absence; an omitted field does not act as a wildcard.
Zero budget remains zero and is checked exactly.
Actor capability, target complexity, control scope, retry policy, target population and recovery metadata must also match when either side declares them.
Structured contexts preserve JSON type distinctions, including bool versus integer.
The resolver forwards these fields and governance instead of dropping the caller's policy.

History matching uses exact ordered identities.
Changing an earlier context hash, using a technique-only identity, using `default` in place of a hash, reordering, or removing an earlier event cannot reuse the original record.
Missing, empty and contradictory registry history is an integrity refusal, so later providers cannot hide it.
The provider never projects aliases implicitly.
Different complete contextual records can coexist; duplicate applicable records remain a conflict.
